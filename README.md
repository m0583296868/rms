# RMS — ניהול פניות

מערכת לניהול פניות שמגיעות מארגונים ומעסיקים. כמה משתמשים יכולים לעבוד במקביל, והשליפה נשארת בצד השרת גם כשיש כמות גדולה של רשומות.

המבנה זהה לפרויקט MSMA: שרת ASP.NET Core בשכבות Controllers / BL / DAL, וקליינט Angular עם Angular Material.

## טכנולוגיות

| חלק | טכנולוגיה |
| --- | --- |
| שרת | .NET 10, ASP.NET Core. 
| גישה לנתונים | Entity Framework Core 9, SQL Server |
| מיפוי | AutoMapper 13 |
| תיעוד API | Swagger |
| קליינט | Angular 19, Angular Material 19, RxJS 7 |
| בדיקות | xUnit, WebApplicationFactory, SQLite |

## הרצה

1. במחשב הזה SQL Server המלא לא מותקן, ויש LocalDB. מחרוזת החיבור ב-`SERVER/appsettings.Development.json` מצביעה ל-`(localdb)\MSSQLLocalDB` ולבסיס `RMSDB`. אם עובדים מול שרת אחר, משנים רק את השורה הזו.
2. מהתיקייה `SERVER`:

```bash
dotnet run
```

בהפעלה הראשונה נוצר בסיס הנתונים והטבלאות, כולל האינדקסים. השרת עולה על `http://localhost:5080`, ו-Swagger ב-`http://localhost:5080/swagger`.

3. מהתיקייה `CLIENT`:

```bash
npm install
npm start
```

המסך נפתח ב-`http://localhost:4200`.

4. במסך, בשדה «מי מעדכן» רושמים שם. בתחתית המסך אפשר ליצור נתוני בדיקה. ברירת המחדל היא 100,000 רשומות, והיצירה מוחקת את הנתונים הקודמים ויוצרת אותם מחדש. עם 100,000 רשומות זה יכול לקחת בערך דקה עד שתי דקות.

5. בדיקות:

```bash
dotnet test RMS.Tests
```

הבדיקות לא נוגעות ב-SQL Server. הן מרימות את ה-API מול SQLite בזיכרון.

## פנייה

שדות: `Id`, `Title`, `OrganizationName`, `Status`, `Priority`, `AssignedTo`, `CreatedAt`, `UpdatedAt`, `Version`.

סטטוסים: `New`, `InProgress`, `Waiting`, `Completed`.

עדיפויות: `Low`, `Medium`, `High`.

מעברים מותרים:

- מחדש אפשר לעבור לבטיפול או לממתין
- מבטיפול אפשר לעבור לממתין או להושלם
- מממתין אפשר לעבור לבטיפול או להושלם
- מהושלם אין מעבר

## API

| קריאה | תפקיד |
| --- | --- |
| `GET /api/Request` | רשימה עם סינון, חיפוש, מיון ודפדוף |
| `GET /api/Request/{id}` | פנייה אחת |
| `GET /api/Request/summary` | סיכום לפי סטטוס ולפי עדיפות |
| `GET /api/Request/{id}/history` | היסטוריית שינויי סטטוס |
| `PUT /api/Request/{id}/status` | עדכון סטטוס |
| `POST /api/Request/bulk-status` | עדכון סטטוס עד 100 פניות |
| `POST /api/Request/seed` | יצירה מחדש של נתוני בדיקה |

פרמטרים לרשימה: `page`, `pageSize` (1 עד 100), `status`, `priority`, `organizationName`, `assignedTo`, `from`, `to`, `search`, `sortBy`, `sortDir`.

מיון אפשרי לפי `createdAt`, `updatedAt`, `title`, `organizationName`, `priority`, `status`, בכל כיוון `asc` או `desc`.

חיפוש רץ על הכותרת ועל שם הארגון. סינון המטפל הוא התאמה מדויקת, כדי שאפשר יהיה להשתמש באינדקס.

שגיאות חוזרות כ-Problem Details:

- 400 קלט לא תקין או מעבר סטטוס אסור
- 404 פנייה שלא קיימת
- 409 עדכון על גרסה ישנה

## למה לא נטענים כל הנתונים לזכרון

`RequestDal.Get` בונה `IQueryable`. כל הסינון, המיון, ה-`Count`, ה-`Skip` וה-`Take` רצים בבסיס הנתונים. `ToList` נקרא רק אחרי הדפדוף, אז לזכרון נכנס עמוד אחד (לכל היותר 100 שורות).

הסיכומים הם `GROUP BY` עם `Count`. גם הם לא מושכים את הטבלה לזכרון.

יצירת נתוני הבדיקה נעשית במנות של 2,000, ובמחיקה משתמשים ב-`ExecuteDelete` כדי לא לטעון את כל השורות.

## ביצועים

נבדקו שתי פעולות אחרי טעינה של 100,000 רשומות ל-LocalDB:

1. שליפת עמוד. סינון `status=InProgress` ו-`priority=High`, מיון לפי `createdAt`, גודל עמוד 20. חזרו 20 שורות מתוך 8,333, בערך 160 מילישניות אחרי שהתוכנית כבר הייתה בזיכרון. שאילתה עם חיפוש טקסט נוסף על אותם סינונים לקחה בערך 300 מילישניות. הזמן נכתב גם ללוג של השרת: `List query ... in {Ms} ms`.
2. סיכום הכמויות. החישוב הראשון לקח בערך 280 מילישניות. קריאה שנייה, מהמטמון, לקחה בערך 6 מילישניות. בלוג: `Summary aggregation took {Ms} ms`, ובפעם השנייה `Summary cache hit`.

יצירת 100,000 הרשומות עצמה לקחה בערך 39 שניות, במנות של 2,000.

תוכנית הביצוע של השליפה המרכזית, אחרי `SET SHOWPLAN_TEXT` על 100,000 הרשומות:

`Index Seek` על `IX_Requests_Status_Priority_CreatedAt` לפי סטטוס ועדיפות, בלי מיון נפרד, כי האינדקס כבר מסודר לפי `CreatedAt` יורד ואז `Id`.

הסיכום הוא `GROUP BY` על כל הטבלה. זו הסיבה שהוא נשמר במטמון, והפגיעה במטמון נכתבת ללוג: `Summary cache hit`.

צוואר בקבוק: חיפוש עם `Contains` מתורגם ל-`LIKE '%טקסט%'`. אינדקס רגיל לא עוזר כשיש אחוז בתחילת התבנית, ובטבלה גדולה זו סריקה. שיפור מתאים הוא Full-Text Index על `Title` ועל `OrganizationName`.

## Concurrency

לכל פנייה יש `Version`. העדכון שולח את הגרסה שהמסך קרא. אם הגרסה בבסיס כבר אחרת, השרת מחזיר 409 ולא משנה את השורה.

בנוסף, Entity Framework כותב את התנאי `WHERE Version = הגרסה שהתקבלה` בתוך ה-`UPDATE`. אם שני עדכונים עוברים את הבדיקה בזיכרון באותו רגע, רק אחד נשמר, והשני מקבל `DbUpdateConcurrencyException` וגם הוא חוזר כ-409. ככה אין עדכון שנדרס.

`UpdatedAt` ו-`Version` מתעדכנים באותו `SaveChanges` יחד עם שורת ההיסטוריה. אם השמירה נכשלת, גם ההיסטוריה לא נשמרת.

נבחר מספר שלם ולא `rowversion` של SQL Server, כי את המספר פשוט להחזיר ללקוח ולשלוח בחזרה. `rowversion` היה עושה את אותו תפקיד, אבל דורש להעביר מערך בתים ב-JSON.

## Bulk

`POST /api/Request/bulk-status` מקבל עד 100 פניות. ההתנהגות היא הצלחה חלקית: כל פנייה נשמרת בנפרד. פנייה שלא קיימת, פנייה עם גרסה ישנה, או מעבר סטטוס אסור נכנסת ל-`failed` עם הסיבה (`NotFound`, `Conflict`, או טקסט הוולידציה). השאר נכנסות ל-`succeeded`.

זו הבחירה ולא «הכל או כלום», כי בעבודה שוטפת אין סיבה לבטל 90 עדכונים תקינים בגלל פנייה אחת שהשתנתה אצל מישהו אחר. הבקשה עצמה נדחית ב-400 אם היא ריקה, אם יש בה יותר מ-100 פניות, או אם אותו מזהה מופיע פעמיים.

## היסטוריה

כל שינוי סטטוס נשמר עם `RequestId`, `PreviousStatus`, `NewStatus`, `ChangedAt`, `ChangedBy`. צופים בה דרך `GET /api/Request/{id}/history` ודרך הכפתור «היסטוריה» במסך.

## Cashe

נשמר סיכום אחד: כמויות לפי סטטוס ולפי עדיפות. זה נתון שנקרא בכל כניסה למסך, והוא יקר יחסית כי הוא סופר את כל הטבלה, אבל התוצאה שלו קטנה.

- תפוגה: 2 דקות
- ביטול: אחרי עדכון סטטוס, אחרי עדכון מרוכז, ואחרי יצירת נתוני בדיקה המפתח `requests-summary` נמחק

`IMemoryCache` חי בתוך תהליך אחד. בכמה מופעי שרת צריך להחליף אותו ב-`IDistributedCache` (למשל Redis) עם אותו מפתח ואותה מחיקה אחרי עדכון. התפוגה נשארת רשת ביטחון אם מחיקה לא הגיעה.

## שתי החלטות

1. SQL Server ולא MongoDB. הסינון המשולב, האגרגציות, האינדקסים והטרנזקציה של סטטוס יחד עם היסטוריה יושבים טבעי בבסיס טבלאי. MongoDB היה מתאים למסמך גמיש, אבל פחות נוח לעדכון  
2. עדכון מרוכז עם הצלחה חלקית ולא טרנזקציה אחת לכל הבקשה. טרנזקציה אחת פשוטה יותר לעקביות, אבל מפילה עבודה תקינה בגלל שורה אחת. התשובה מפרטת לכל שורה אם היא הצליחה ולמה היא נכשלה.

## מגבלה ושיפור

החיפוש הטקסטואלי עם `Contains` לא יכול להשתמש באינדקס רגיל. השיפור הוא Full-Text Index על הכותרת ושם הארגון.

## Tests

שש בדיקות אינטגרציה ב-`RMS.Tests`, מול ה-API ו-SQLite:

- שליפה עם סינון סטטוס ודפדוף, כולל בדיקה שחוזר עמוד ולא כל הרשומות
- גודל עמוד לא חוקי
- מעבר סטטוס אסור
- עדכון מוצלח, ואחר כך עדכון עם אותה גרסה שמקבל 409, ובדיקה שההיסטוריה נשמרה פעם אחת
- פנייה שלא קיימת
- עדכון מרוכז שבו שורה אחת מצליחה ושורה חסרה מדווחת

## מסך

החיפוש מחכה 300 מילישניות ורק אז נשלח. כל טעינה חדשה מבטלת את הקודמת באמצעות `switchMap`. יש מצב טעינה, מצב ריק ומצב שגיאה. עדכון סטטוס שמקבל 409 מציג הודעה וכפתור רענון. הסיכום וההיסטוריה מוצגים באותו מסך. הקריאות לשרת נמצאות ב-`RequestsService`, והמסך לא בונה כתובות בעצמו.
